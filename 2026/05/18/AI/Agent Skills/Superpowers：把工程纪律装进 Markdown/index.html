Superpowers：把工程纪律装进 Markdown

把一套工程方法论，压缩成一文件夹 Markdown，让任何 AI 编程助手都老老实实照着做

一句话定位

Superpowers 是一个开源的、跨平台的 agentic skills 框架，也是一套完整的 AI 编程方法论。它用十几个 SKILL.md 文件，把”先想清楚再动手、写测试再写代码、改完先验证再宣称完成”这些老生常谈的工程纪律，固化成 AI 必须遵守的工作流

它由 Jesse Vincent（GitHub ID：obra）在 2025 年 10 月创建，托管在 github.com/obra/superpowers，MIT 协议。截至 2026 年 7 月，已经积累 25 万多 Star，是当前 Vibe Coding 领域最受关注的”AI 工程纪律”框架之一

和 Spec Kit、Open Spec 这类 SDD 工具不同，Superpowers 解决的不是”怎么写规范”，而是”怎么让 AI 真的按规矩干活”——它管的是执行层的纪律，而不是需求层的规范

AI 编程纪律基础

AI 编程助手的”知行脱节”

要理解 Superpowers 解决的问题，先得承认一个尴尬的事实：现代 AI 编程助手能力很强，但翻车的方式高度一致

  • 它先写代码，再补测试，然后忘了跑测试
  • 它因为”失败的例子现在看起来能跑了”，就宣布 Bug 修好了
  • 它只治标不治本，从不调查根因
  • 它声称构建通过，但其实根本没跑构建
  • 当你质问它时，它其实完全知道本该怎么做

这些不是知识盲区。你让 AI 给你讲 TDD，它讲得头头是道——这些概念早就在它的训练数据里了。它缺的不是”知道”，而是一个在捷径更诱人时逼它守规矩的机制

这正是 Superpowers 想填的那个坑


Superpowers 简介

Superpowers 的核心思路可以用一句话概括：AI 编程助手缺的不是能力，而是纪律；而纪律可以用纯文本分发

它整个项目异常轻量，只有三样东西：

  1. 一个 skills/ 目录，里面是十几个 SKILL.md 文件，每个文件几百字，讲一种工程实践：TDD、调试、头脑风暴、写计划、代码评审、完成前验证
  2. 一个 session-start 钩子，在每次会话开始时注入一段不到 2000 token 的引导文档，告诉 AI”在做任何事之前，先检查有没有合适的 skill”
  3. 每个宿主平台一份薄薄的插件清单（.claude-plugin/、.cursor-plugin/ 等），让各家 AI 工具用自己的方式发现同一批 skill

没有微调过的模型，没有专有 SDK，没有 Agent 平台。工程文化，作为一个 Git 仓库分发，你一个小时就能通读一遍


为什么需要 Superpowers

Vibe Coding 时代，AI 编程助手最大的问题不是”不会写代码”，而是”管不住自己”。它会：

  • 跳步：你让它先设计再写，它直接开写
  • 自欺：测试没跑就说测试过了
  • 脑补：需求模糊的地方自己拍板，拍得特别自信
  • 走捷径：每次都是”就这一次”例外

靠提示词能缓解，但治标不治本。提示词一长，AI 就忘；换一次对话，所有约定归零

Superpowers 的做法是把纪律写进文件、用钩子在每次会话开头强制注入，让”守规矩”变成工具的内置行为，而不是靠人去盯。这和 Spec Kit 的门禁系统思路一脉相承，只是 Spec Kit 管的是”需求阶段”，Superpowers 管的是”执行阶段”


设计哲学

Superpowers 的设计理念可以归纳成几条非常清晰的原则：

  • Mandatory, not Suggested 强制而非建议：skill 不是”参考文档”，是 AI 必须检查并调用的强制工作流
  • 1% Rule 1% 规则：只要有 1% 的可能某个 skill 适用于当前任务，就必须调用它
  • Iron Laws 铁律：每个刚性 skill 开头都有一条大写的、不可商量铁律，后面跟着一张”红旗”表，列出 AI 最可能用来给自己开脱的借口
  • Systematic over Ad-hoc 系统化胜过临时起意：用固定流程替代直觉，比如 systematic-debugging 强制四阶段流程
  • Isolation & Safety 隔离与安全：强制用 git worktree 隔离工作区，保证干净的基线
  • Harness-Agnostic 工具无关：同一份 skills/ 目录，喂给 Claude Code、Cursor、Codex、Copilot CLI、OpenCode 等十来家 AI 工具

其中最值得品味的是 Iron Laws + Red Flags。它不是励志标语，而是把一个资深工程师的 Code Review 意见，编码成了指令。它的目标不是”教 AI 规矩”——AI 早就会了——而是防止 AI 说服自己不守规矩

核心概念

Skill 技能

Skill（技能）是 Superpowers 里可复用、模块化的 AI 指令单元，给编程助手提供结构化的工作流。和静态提示词不同，skill 是动态指令——AI 根据当前任务，通过工具调用去发现并调用合适的 skill

每个 skill 就是一个 SKILL.md 文件，住在一个独立目录里，遵循统一的格式：YAML frontmatter（元数据，用于被发现）+ Markdown 正文（真正的指令）

Skill 不是被动参考文档，而是主动的流程定义。AI 必须在做相关任务之前先去检查有没有对应 skill，并通过平台原生工具调用它。这套机制由 using-superpowers 元技能在会话启动时强制注入

特性 Skill 普通文档
发现方式 通过工具调用搜索 需手动浏览
调用方式 平台原生工具集成 Read 工具或直接访问
优化目标 Claude Search 优化(CSO) 标准技术写作
验证方式 用 TDD 方法论压测过 通常未测试
强制性 强制检查协议(1% 规则) 可选参考
结构 严格 YAML + 分节 自由 Markdown

SKILL.md 与 CSO

每个 skill 的 SKILL.md 文件由两部分组成：

第一部分：YAML frontmatter，包含 skill 的身份信息和”触发描述”——AI 用它来判断当前上下文该不该用这个 skill

第二部分：Markdown 正文，通常包含：指令优先级、流程定义、红旗表（AI 用来跳过 skill 的常见借口，配对应的现实校验）

这里有个关键概念叫 CSO（Claude Search Optimization，Claude 搜索优化）。description 字段是 CSO 的主战场——Claude 靠它决定要不要加载完整的 SKILL.md。CSO 有三条硬要求：

  • 触发导向：以 “Use when…” 开头，聚焦”什么时候用”
  • 第三人称：描述会被注入系统提示词，人称不一致会影响发现
  • 不写流程细节：如果 description 把流程总结了一遍，Claude 可能照着摘要做，跳过完整 skill 内容

最后一条最反直觉——很多人写文档喜欢把摘要写全，但在 skill 里，摘要写全反而害了 AI


using-superpowers 元技能

using-superpowers 是整个系统的”元技能”，也是唯一一个在每次会话开头被钩子强制注入的 skill。它不教 AI 具体怎么写代码，它教 AI 怎么用 skill 系统

它建立了一套强制协议：在做任何回应之前——包括问澄清问题、探索代码库——AI 必须先检查有没有相关 skill。在 v6.1.0 里，这段引导被压缩以降低每次会话的 token 成本，但保留了”红旗”反合理化规则和用户指令优先级规则

打个比方，using-superpowers 就像新员工入职第一天发的《员工手册》扉页：它不教你具体业务，它教你”遇到事先翻手册”


1% Rule 1% 规则

1% 规则是 Superpowers 最核心的强制机制，一句话：只要有 1% 的可能某个 skill 适用于当前任务，AI 就必须调用它

这条规则必须发生在任何回应之前。你不能”先看看代码再说”——看代码之前也得先查 skill。这听起来有点轴，但正是这种”宁错杀不放过”的态度，把”守规矩”从靠自觉变成了靠机制


Iron Laws 铁律与 Red Flags

读多了 skill 文件会发现一个固定模式：每个刚性 skill 开头都有一条大写的、不可商量的铁律，后面跟着一张红旗表——列出 AI 最可能用来跳过这条规则的借口，配上对应的现实校验

比如 TDD skill 的铁律是：

NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
（没有失败的测试，就不许写生产代码）

验证 skill 的铁律是：

NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
（没有新鲜的验证证据，就不许宣称完成）

调试 skill 的铁律是：

NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
（没有根因调查，就不许动手修）

配套的红旗表非常不留情面。TDD 会把”测试一次就过了”、”保留删掉的代码当参考”、”就这一次例外”全列出来打脸；验证 skill 会把”应该”、”大概”、”看起来”这些词全标红

这些不是励志海报，它们读起来就像资深工程师 Code Review 意见的指令化版本。目标不是教 AI 规矩，而是防止 AI 说服自己不守规矩


指令优先级

为了确保用户始终掌控，Superpowers 有一条严格的优先级：

  1. 用户的显式指令（CLAUDE.md、AGENTS.md、直接请求）——最高
  2. Superpowers skills——覆盖默认行为
  3. 默认系统行为——最低

也就是说，如果你明确说”这次不用 TDD”，AI 会听你的。Superpowers 是纪律，不是枷锁；用户永远有最终否决权

技能库

brainstorming 头脑风暴

brainstorming 是流程类 skill，它有一条硬门禁：在 AI 问完澄清问题、并提出一个你能接受的设计之前，不许写代码

它的工作方式是苏格拉底式——通过提问帮你把模糊想法打磨成具体设计，然后把设计文档存下来。这里有一道人工审批门：AI 把设计呈现给你，你点头了才能往下走。在 AI 跳进代码或实现类 skill 之前，这道门必须先过

brainstorming 解决的是”AI 是个特别自信的实习生”这个问题。你给它模糊需求，它立刻动手，做得特别起劲——但很可能做的根本不是你想要的。brainstorming 让 AI 在动手前先和你对齐方向


writing-plans 编写计划

writing-plans 把一个功能拆成一系列 2-5 分钟的小任务，每个任务都写明：要改哪个文件、测试怎么写、验证步骤是什么。在动手碰任何代码之前，计划先落到 docs/superpowers/plans/ 里

任务粒度是关键。太粗了 AI 容易跑偏，太细了又啰嗦。”2-5 分钟”这个粒度，是为了让每个任务都值得一个全新评审者来把关，也方便回滚

这里也有第二道人工审批门：计划写完后，AI 会让你选执行模式（子代理驱动 or 分批执行），你选了才开始干。两道人工门——设计审批、计划审批——是 Superpowers 防止 AI 脱缰的关键


test-driven-development 测试驱动开发

test-driven-development 强制经典的 RED-GREEN-REFACTOR 循环：写失败测试 → 确认失败 → 写最少代码让它通过 → 确认通过 → 提交

它的铁律前面提过：没有失败的测试，就不许写生产代码。更狠的是，如果你说”我等会再补测试”，它会要求你删掉已写的实现，从头来过

这个 skill 是 Iron Laws + Red Flags 模式的最佳样本。它的红旗表会拦下”测试一次就过了”（一次过说明测试没价值）、”保留删掉的代码当参考”（污染上下文）、”就这一次例外”（每次都是这一次）


systematic-debugging 系统化调试

systematic-debugging 是一个四阶段流程，铁律是：没有根因调查，就不许动手修

它明确禁止”修你还没理解的东西”。AI 不能因为”失败的例子现在看起来能跑了”就宣布 Bug 修好了——那只是治标。它必须先复现、再定位根因、再修、再验证

这个 skill 直接针对 AI 调试时最常见的翻车方式：打补丁、治标不治本、从不查根因


verification-before-completion 完成前验证

verification-before-completion 的铁律：没有新鲜的验证证据，就不许宣称完成

它要求 AI 自己去跑验证命令，并真的读输出，然后才能说”做完了”。它会把”应该”、”大概”、”看起来”这些词全标红——这些是 AI 最爱用来糊弄完成状态的话术

这个 skill 解决的是”AI 声称构建通过但其实根本没跑构建”的痼疾。它把”宣称完成”从一句空话，变成了必须有证据支撑的结论


using-git-worktrees 工作区隔离

using-git-worktrees 强制用 git worktree 隔离每个开发分支，保证一个干净的基线，防止未提交的改动污染 AI 的上下文

从 v6.0.0 起，worktree 从全局目录（~/.config/superpowers/worktrees/）改成了项目本地 .worktrees/ 目录，隔离性和上下文感知都更好。SDD 的临时文件（任务简报、实现者报告、进度账本）则放在一个会自动 gitignore 的 .superpowers/sdd/ 目录里，避免碰到某些平台（如 Claude Code）对 .git/ 的保护限制


subagent-driven-development 子代理驱动开发

subagent-driven-development（SDD）是 Superpowers 的执行核心，后面会专门展开。简单说：每个任务派一个全新子代理去实现，再派另一个子代理去评审，控制器统筹全局


其余协作与收尾技能

  • executing-plans：SDD 的替代方案，在当前会话分批执行任务，带检查点供人审
  • requesting-code-review / receiving-code-review：主动请求评审、正确接收反馈，按严重度报告问题
  • dispatching-parallel-agents：并发派发多个子代理
  • finishing-a-development-branch：验证测试、选择合并或开 PR、清理 worktree
  • writing-skills：按最佳实践写新 skill，本身也用 TDD 方法论压测

工作流程

完整流水线

Superpowers 强制一条从想法到合并的线性流水线，由 skill 串联而成。完整流程覆盖设计探索 → 隔离工作区 → 任务拆解 → 子代理执行 → 任务间评审 → 分支收尾

一句话概括：先头脑风暴想清楚（brainstorming），开个隔离工作区（worktree），把活拆成小任务（writing-plans），派子代理逐个实现（SDD），任务间做代码评审（code-review），最后验证测试、合并、清理（finishing）


两道人工审批门

整条流水线里有两道强制的人工审批门，没有明确确认就不许往下走：

  1. 设计审批门——由 brainstorming 守。AI 把设计呈现给你，在你批准之前，禁止跳进代码或实现类 skill
  2. 计划审批门——由 writing-plans 守。计划写完后，AI 让你选执行模式，你选了才开始执行

这两道门是 Superpowers 区别于”全自动 Agent”的关键。它不追求”一句话生成完整项目”的炫技，而是把人留在关键决策点上，确保 AI 不会在错误方向上越跑越远


执行模式选择

计划批准后，AI 在两种执行模式里选一种：

模式 Skill 行为
子代理驱动 subagent-driven-development 每个任务派全新子代理，两阶段评审（规范合规 + 代码质量）
分批执行 executing-plans 在当前会话分批执行，带检查点供人审

两种模式都遵循计划里定义的任务粒度，并强制 RED-GREEN-REFACTOR：写失败测试 → 确认失败 → 写最少代码通过 → 确认通过 → 提交

子代理驱动是推荐模式，因为它能防止上下文污染、支持专门化的评审循环。如果当前平台不支持子代理（Task 工具），就回退到分批执行


SDD 子代理驱动开发详解

SDD 是 Superpowers 流水线的执行核心。它的核心架构把”控制器”（维护全局计划状态）和”子代理”（执行隔离工作单元）分开

几个关键设计：

  • 每个任务一个全新子代理：每个实现者都从干净上下文开始，防止前面任务的上下文污染
  • 产物隔离：短命产物（简报、报告、diff）存在 .superpowers/sdd/ 里，由 sdd-workspace 管理，避免控制器上下文膨胀
  • 任务级评审：评审者只看 diff 和任务简报，不爬整个代码库，除非发现具体风险
  • 修复门槛：只有 Critical 和 Important 级别的问题才强制”修完再评”，Minor 不阻塞

模型选择策略是 SDD 的一大亮点，按任务复杂度分配不同档位的模型：

任务类型 模型档位 复杂度信号
机械型 便宜/快 隔离函数、清晰规范、1-2 个文件，计划含完整代码
集成型 标准/中档 多文件协调、模式匹配、调试
架构型 最强 设计判断、广泛终审、复杂并发

这里有一条很反直觉的原则：**”轮数比 token 单价更重要”**。便宜模型在多步任务上经常要跑 2-3 倍的轮数，按墙钟时间和上下文算下来，反而比中档模型更贵

评审者协议也很有意思。评审者被要求”不要相信实现者报告”——必须对着实际 diff 验证实现者的声明，把实现者的设计理由（比如”按 YAGNI 留着了”）当成待评判的声明，而不是结论。问题按严重度分三档：Critical（必须修，行为/数据/安全）、Important（应该修，可维护性）、Minor（锦上添花）

状态协议——实现者子代理会回报四种状态，控制器要分别处理：

状态 含义 控制器动作
DONE 任务完成 进入任务评审
DONE_WITH_CONCERNS 完成但有疑虑 处理疑虑，次要则进入评审
NEEDS_CONTEXT 缺信息 补充上下文重新派发
BLOCKED 无法完成 升级模型/拆任务/升级到人

架构与多平台

双仓库设计

从 v2.0.0 起，Superpowers 采用双仓库设计：一个轻量的插件垫片（obra/superpowers 主仓库）+ 一个共享的 skills 仓库（通过 SUPERPOWERS_SKILLS_ROOT 引用）。这种分离让插件和 skills 可以独立版本、独立更新——平台基础设施的改动不用每次都重装插件，skill 的微调也能自动拉取

方面 插件仓库 obra/superpowers Skills 层
版本 语义化版本（如 6.1.1） 滚动/基于提交
发布 基础设施改动 持续（skill 微调）
更新 手动/市场更新 自动（git pull）
宿主 Claude、Codex、Cursor 等 所有宿主统一

多平台集成

Superpowers 最有意思的一点是：同一份 skills/ 目录，喂给十来家 AI 工具。每个宿主拿一份薄薄的清单，用自己的发现机制指向同一批 Markdown。skills 本身是宿主无关的——它是可移植的工程文化，不是某家 Agent 的功能。

平台工具映射

skill 用 Claude Code 的工具名（Skill、Task、TodoWrite、Read/Write/Edit）来写。为了保持模块化，Superpowers 给其他平台提供了一层映射。比如 Copilot CLI：

Claude Code 工具 Copilot CLI 等价物 用途

这种”以 Claude Code 工具名为准 + 平台映射层”的设计，让 skill 主体保持厂商中立，平台差异全交给映射层和宿主专属参考文件处理

模型选择建议

Superpowers 官方推荐用高推理能力的模型，无论是设计阶段还是实现阶段。原因和 Spec Kit、Open Spec 一致：SDD 的核心价值在于”想清楚再动手”，而”想清楚”对模型推理能力要求很高

但 SDD 在模型选择上更精细——它按任务复杂度分配模型档位（机械型用便宜的、架构型用最强的），而不是一刀切。这里的关键原则是”轮数比 token 单价重要”：便宜模型在多步任务上跑的轮数多，总成本反而可能更高

另外，Superpowers 同样强调上下文卫生。每个子代理都从干净上下文开始，正是这个原则的体现——让 AI 专注于当前任务，不要被无关历史干扰


适用场景

Superpowers 不是所有场景都适合。判断标准是：这个任务值不值得走完一整套纪律流程

适合用 Superpowers 的场景：

  • 需要设计探索的新功能（先 brainstorming）
  • AI 容易走捷径、跳测试的任务（TDD 强制）
  • 难调的 Bug（systematic-debugging 强制查根因）
  • 多任务、需要隔离上下文的特性（SDD 子代理）
  • 对完成质量有要求、不能糊弄的场景（verification 强制验证）

不太适合的场景：

  • 改个文案、调个颜色这种一行改动
  • 探索性原型（目标是发现需求，不是实现需求）
  • 平台不支持子代理（只能用分批执行，体验打折）
  • 一次性脚本，没有后续维护预期

简单说，越重要、越复杂、越怕 AI 走捷径的任务，越值得用 Superpowers；越简单、越一次性的事，Vibe Coding 直接上反而更快


既有项目改造

Superpowers 对既有项目很友好——它本质上是”给 AI 加纪律”，不动你的代码结构。你不需要先把整个系统文档化，正确的做法是：

  1. 装上插件
  2. 下次要改某个功能时，让 AI 走一遍 brainstorming → plan → SDD
  3. 改完，worktree 清理掉，不留痕迹
  4. 随着你不断用它，AI 的工程纪律会稳定地体现在每次改动里

这种”用着用着就规范了”的策略，让既有项目的接入成本几乎为零

与其他工具对比

vs Spec Kit / Open Spec

Spec Kit 和 Open Spec 是 SDD 工具，Superpowers 是 skills 框架，三者定位不同但互补：

维度 Spec Kit / Open Spec Superpowers
管的是哪层 需求层（写规范） 执行层（怎么干活）
核心产物 spec.md / plan.md / tasks.md SKILL.md 工作流
强制机制 阶段门禁（没 spec 不能 plan） 1% 规则 + Iron Laws + 两道人工门
形态 CLI + 斜杠命令 插件 + session 钩子
解决的问题 “AI 写的不是你想要的” “AI 管不住自己、走捷径、跳测试”

打个比方：Spec Kit / Open Spec 像是给 AI 一份正式的施工图纸，让它照着盖楼；Superpowers 像是给 AI 一本《施工操作规程》，告诉它砌砖前先拌砂浆、上梁前先测水平。两者完全可以一起用——先写规范，再用 Superpowers 执行


vs 无规范

最值得对比的还是”什么纪律都不用”的 Vibe Coding 状态。不用任何框架时，AI 的表现完全靠提示词和运气：

  • 它先写代码再补测试，然后忘了跑
  • 它因为”看起来能跑了”就宣布 Bug 修好
  • 它只治标不治本
  • 它声称构建通过但根本没跑

Superpowers 把这些”老生常谈但没人守”的工程纪律，从靠自觉变成了靠机制。它带来的不是更重的流程，而是让 AI 真的按它本就知道的规矩干活


vs Kiro / 单一 IDE 方案

Kiro 是 AWS 的 AI 编程 IDE，内置 SDD 能力但锁死在自家 IDE 里。Superpowers 的核心优势是工具无关——同一份 skills 喂给十来家 AI 工具，你今天用 Cursor，明天换 Claude Code，纪律文件原封不动地跟着走，不会被任何一家厂商绑死

这其实就是开放标准的价值。MCP 解决了”AI 连接工具”的标准化，Spec Kit / Open Spec 想解决”AI 读写规范”的标准化，而 Superpowers 想解决的是”AI 执行工程实践”的标准化

Superpowers 与 Vibe Coding 的关系

Superpowers 是 Vibe Coding 走向成熟的产物，但它走的路和 SDD 工具不一样

Vibe Coding 是”跟着感觉写代码”，Agentic Engineering 是”按流程管 AI”。SDD 工具（Spec Kit、Open Spec）把”管 AI”落在了需求层——先写规范再动手；Superpowers 把”管 AI”落在了执行层——动手时必须守工程纪律

两者解决的是同一个大问题的不同面：AI 编程时代，最大的瓶颈不是 AI 不会写代码，而是 AI 管不住自己。模型早就在训练数据里见过无数 TDD、调试、验证的最佳实践，你让它讲它讲得头头是道——但真到干活时，捷径总是更诱人

Superpowers 的洞察是：AI 缺的不是知识，是纪律；而纪律可以用纯文本分发。它把资深工程师的 Code Review 意见、把”先测试后代码””改完先验证再宣称完成”这些老生常谈，编码成 Iron Laws 和 Red Flags，用 session 钩子在每次会话开头强制注入，用 1% 规则逼 AI 在每个任务前先翻手册

它和 SDD 工具不是竞争，是互补。你可以先用 Spec Kit 把需求写清楚，再用 Superpowers 让 AI 严格按 TDD、按子代理评审流程去实现。一个管”做什么”，一个管”怎么做”

可以说，谁掌握了用 Superpowers 这类工具把 AI 的执行纪律管好，谁就真正让 AI 编程助手从”会写代码的实习生”升级成了”守规矩的工程师”。模型是商品，工具是商品，唯有”把工程纪律变成可执行、可分发、可强制的文本”的能力，是 AI 替代不了的——而这，正是 Superpowers 给出的答案

附：速查表

三句话记住 Superpowers

  1. 它是一文件夹 Markdown（14 个 SKILL.md），把工程纪律编码成 AI 必须调用的强制工作流
  2. 它靠一个 session 钩子 + 1% 规则，逼 AI 在每个任务前先查 skill、按规矩干活
  3. 它跨十来家 AI 工具通用，是”可移植的工程文化”，不是某家 Agent 的功能
