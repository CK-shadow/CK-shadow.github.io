Agent Skill 创建指南

发表于2026-05-27|更新于2026-07-30|AI
|浏览量:

Agent Skill 基础

为什么需要 Skill

Vibe Coding 时代，你可能已经遇到过这些重复劳动：

  • 每次部署 staging，都要在 Chat 里粘贴一长段「先跑测试、再构建、再推镜像、再通知 Slack」
  • 每次写 commit message，都要提醒 Agent「按 Conventional Commits、分析 git diff、写 1-2 句 why」
  • 每次 Code Review，都要重申「按严重度分级、不要只夸不挑刺」

靠 Rules 能缓解一部分——但 Rules 适合短而稳的约束，不适合塞进去一整套多步骤流程。塞多了，上下文窗口被占满，和当前任务无关的内容也一起加载

Skill 的设计思路是按需加载：

  1. 启动时，Agent 只看到每个 Skill 的 name 和 description（几十 token）
  2. 任务匹配时，才读取完整 SKILL.md
  3. 执行过程中，才按需读取 references/ 或运行 scripts/

这意味着你可以在手边备十几个 Skill，而不会像把十几页 Prompt 全塞进 Rules 那样撑爆上下文


Skill 是什么

Agent Skill（智能体技能）是一种开放标准（agentskills.io），用纯 Markdown 把「怎么做某类事」封装成可复用的工作流包。每个 Skill 就是一个目录，核心是 SKILL.md——YAML 元数据告诉 Agent「什么时候用」，Markdown 正文告诉 Agent「具体怎么做」

Cursor 从 2.4 版本起原生支持 Agent Skills。你可以用内置的 /create-skill 向导快速创建，也可以手写 SKILL.md 精细打磨。Skill 和 Rules 互补：Rules 管「底线和规范」，Skill 管「流程和专项能力」


一个 Skill 本质上是一个版本可控的文件夹：

它不是一个新模型，也不是专有 SDK。它就是 Markdown + 可选脚本，任何支持 Agent Skills 标准的工具都能读——Cursor、Claude Code、GitHub Copilot、Codex CLI 等

Skill 可以包含：

能力 说明
领域知识 团队特有的流程、命名约定、审批门禁
可重复工作流 多步骤任务的标准化执行顺序
可执行脚本 比让 Agent 现场生成代码更稳定、更省 token
模板与资源 PR 描述模板、报告结构、配置样例

Skill vs Rules vs Prompt

Harness 层有三类「教 Agent 做事」的方式，边界要分清：

维度 Prompt（对话里临时说） Rules（.cursor/rules/） Skills（.cursor/skills/）
持久性 一次性，换对话就丢 持久，每次会话可注入 持久，按需加载
适用内容 临时指令、一次性需求 短而稳的规范、风格约束 多步骤流程、专项工作流
典型例子 「这次别写测试」 「TypeScript 公共 API 必须加类型注解」 「按 TDD 流程实现功能」
加载方式 用户发送 alwaysApply 或文件 glob 匹配 description 匹配或手动 /skill-name
团队共享 不能 提交到仓库即可 提交到仓库即可

一句话：Rules 是「宪法」，Skill 是「操作手册」。不要把整本操作手册抄进宪法里

核心概念

渐进式加载

Agent Skills 标准采用三级渐进披露（Progressive Disclosure），这是 Skill 能「多而不胀」的关键：

阶段 加载内容 时机 上下文成本
Discovery 发现 所有 Skill 的 name + description Agent 启动时 极低
Activation 激活 完整 SKILL.md 正文 任务匹配 description 或用户手动调用 中等
Execution 执行 references/、scripts/、assets/ Agent 执行过程中按需读取 按需

设计 Skill 时要时刻记住：description 是 Discovery 阶段的唯一入口。写不好 description，Skill 写了也白写


存放位置

Cursor 自动从以下目录发现 Skill：

位置 路径 作用域
项目级 .cursor/skills/ 或 .agents/skills/ 当前仓库，可提交 Git 团队共享
个人级 ~/.cursor/skills/ 或 ~/.agents/skills/ 所有项目可用
嵌套目录 apps/web/.cursor/skills/ 仅作用于该子目录下的文件
兼容目录 .claude/skills/、.codex/skills/ 等 跨工具兼容

重要：不要往 ~/.cursor/skills-cursor/ 里写 Skill。那是 Cursor 内置 Skill 的保留目录，由系统自动管理

分类组织也支持子目录——Cursor 会递归扫描，Skill 的身份来自包含 SKILL.md 的那一层文件夹名，不是上层分类名：


触发方式

Skill 有三种激活路径：

  1. 自动匹配：Agent 根据当前任务和 Skill 的 description 判断是否相关，自动加载
  2. 斜杠命令：在 Agent Chat 输入 /skill-name 手动调用
  3. @ 引用：输入 @skill-name 把 Skill 作为上下文附加

如果某个 Skill 只应该在用户明确请求时运行（比如破坏性操作、涉及计费的操作），在 frontmatter 里加：

这样 Agent 不会自动加载，只有手动 /skill-name 才会生效


SKILL.md 基本结构

每个 Skill 必须有一个 SKILL.md，由 YAML frontmatter + Markdown 正文组成：

Frontmatter 字段

字段 必填 说明
name 是 小写字母、数字、连字符，最多 64 字符，必须与父文件夹名一致
description 是 最多 1024 字符，Agent 用来判断相关性的关键字段
paths 否 glob 模式，限定 Skill 只在匹配文件时 surfaced
disable-model-invocation 否 true 时仅手动调用，不自动匹配
metadata 否 任意键值对，存放额外元数据

三种创建方式

方式 适合场景 操作
向导创建 第一次接触、快速原型 Agent Chat 输入 /create-skill，描述你想要的 Skill
手动创建 精细控制、团队规范 建目录 + 写 SKILL.md
迁移转换 已有 Rules 或斜杠命令 Agent Chat 输入 /migrate-to-skills

推荐路径：先用 /create-skill 生成骨架，再手动打磨 description 和正文

写好 description：Skill 的「搜索引擎优化」

为什么 description 最关键

在 Discovery 阶段，Agent 只看 name 和 description 来决定要不要加载完整 Skill。description 写得好不好，直接决定 Skill 能不能被发现

这和 Superpowers 里的 CSO（Claude Search Optimization） 是同一个道理：description 是 Skill 被搜索到的主战场


三条硬规则

1. 第三人称

description 会被注入系统提示词，人称不一致会影响发现：

2. 同时写清 WHAT 和 WHEN

3. 不在 description 里写流程细节

如果 description 把步骤总结了一遍，Agent 可能照着摘要做，跳过完整 SKILL.md 正文——这反而害了 Skill 的效果

编写原则

简洁是美德

上下文窗口是共享资源——对话历史、其他 Skill、Rules、用户请求都在抢空间。默认假设 Agent 已经足够聪明，只补充它不知道的信息

写每一段之前问自己：

  • Agent 真的需要这段解释吗？
  • 能不能假设 Agent 已经知道？
  • 这段文字的 token 成本值不值？

控制 SKILL.md 体量

主文件 SKILL.md 建议不超过 500 行。详细内容拆到 references/ 里，Agent 只在需要时才读

引用层级保持一层深度——从 SKILL.md 直接链到 reference 文件，不要搞 references/deep/nested/doc.md 这种多层嵌套


匹配自由度

不同任务的「容错空间」不同，Skill 的约束粒度也要匹配：

自由度 适用场景 写法
高（文字指引） 多种做法都合理、依赖上下文 Code Review 指南、设计讨论流程
中（模板/伪代码） 有偏好模式但允许变化 报告生成、PR 描述模板
低（具体脚本） 操作脆弱、一致性要求高 数据库迁移、部署脚本

进阶技巧

用 paths 限定作用域

Skill 只和特定文件类型相关时，用 paths 避免无关任务加载：

也支持逗号分隔的字符串写法：

Monorepo 里，把 Skill 放在 apps/web/.cursor/skills/ 下，会自动 scoped 到 apps/web/ 目录——效果和设 paths 类似


从 GitHub 安装 Skill

Cursor 支持从 GitHub 仓库导入 Skill：

  1. 侧边栏打开 Customize
  2. 进入 Rules，点击 Add Rule
  3. 选择 Remote Rule (Github)
  4. 填入 GitHub 仓库 URL

社区里也有不少开源 Skill 集合，GitHub 搜索 .cursor/skills 能找到不少参考


从 Rules 迁移

Cursor 内置 /migrate-to-skills，可以把符合条件的 Rules 和斜杠命令转成 Skill：

  • 动态 Rules：alwaysApply: false 且没有 globs 的 Rules → 标准 Skill
  • 斜杠命令：用户级和工作区级命令 → 带 disable-model-invocation: true 的 Skill

不会迁移的情况：

  • alwaysApply: true 的 Rules（触发机制不同）
  • 有明确 globs 的 Rules（和 Skill 的按需匹配逻辑不同）
  • 用户级 Rules（不在文件系统上）

Cursor 内置 Skill 参考

Cursor 自带一批内置 Skill，可以当作写法参考：

Skill 作用
/create-skill 创建新 Skill 的向导
/create-rule 创建 Rules
/migrate-to-skills Rules/命令迁移
/review 代码评审
/canvas 创建交互式 Canvas 产物
/loop 定时重复执行 Prompt/Skill

在 Agent Chat 输入 / 即可看到完整列表。注意内置 Skill 在 ~/.cursor/skills-cursor/，不要修改那个目录

反模式：这些坑别踩

  1. Windows 风格路径
  1. 给太多选项
  1. 写时间敏感信息
  1. 术语不一致

选一个词贯穿全文，不要混用：

  • ✅ 始终用「API endpoint」（不要混用 URL、route、path）
  • ✅ 始终用「field」（不要混用 box、element、control）
  1. 模糊的 Skill 名
  1. 把整本手册塞进 SKILL.md

详细规范、长篇 API 文档、大量示例 → 拆到 references/。主文件只留 Agent 每次都需要看的核心流程

创建流程速查

四阶段工作流


最终检查清单

  • 核心质量

    • description 具体，包含关键触发词
    • description 同时包含 WHAT 和 WHEN
    • description 用第三人称
    • SKILL.md 正文不超过 500 行
    • 术语全文一致
    • 示例具体，不是抽象描述

    结构

    • name 与文件夹名一致
    • 文件引用只有一层深度
    • 使用了渐进披露（详细内容在 references/）
    • 工作流步骤清晰
    • 没有时间敏感信息

    如果包含脚本

    • 脚本自包含、有清晰错误信息
    • 依赖包有文档说明
    • 使用 Unix 风格路径
    • 明确 Agent 应该执行还是阅读脚本
